crownos-ipc  ·  v0.1.0  ·  protocol revision 0

A brokerless bus for one desktop

CrownOS services talk over plain AF_UNIX stream sockets with a 20-byte binary header, a compile-time method selector, and no daemon in the middle. This is the complete description: wire format, state machines, security model, limits, and the layout of the crate that implements it.

§1 — Design axioms

Six decisions everything else follows from

The protocol exists to let a compositor, a panel, a notification daemon and a handful of CLI tools on a single seat call each other without a session bus. Every rule below is downstream of one of these six choices.

Brokerless

One hop, no daemon

Each service binds its own socket. A message crosses the kernel exactly once. Nothing has to be started before anything else works.

Zero-handshake

The first frame is a request

The kernel authenticates the peer at accept(2). There is no hello, no capability negotiation, no version exchange — nothing to round-trip before real work.

Rigid

Drift fails loudly

A method's selector hashes its signature. A peer compiled against a different argument list gets UNKNOWN_METHOD, never a silently misdecoded struct.

Out-of-band

Bulk data is an fd

Frames carry up to 1 MiB and up to 16 descriptors. A wallpaper or a screencast buffer travels as a memfd, not as bytes on the stream.

Bounded

Every queue has a ceiling

Connections per uid, subscriptions per peer, frames and bytes per outbox, messages per inbox. A slow subscriber loses events instead of wedging the service.

Runtime-agnostic

The core never blocks

A non-blocking state machine over one fd, pumped by whatever loop the process already runs — calloop, tokio, smol, or bare poll(2).

§2 — Topology

What removing the broker actually removes

The trade is deliberate. There is no bus-wide name registry, no activation, no introspection endpoint and no message filtering — a caller that wants to talk to crownpad opens crownpad.sock or fails. In exchange, the transport is a single UnixStream per relationship, authorization is the kernel's answer to SO_PEERCRED, and a service outage is visible immediately as ServiceUnavailable rather than as a hung call into a broker.

§3 — Socket namespace

Addressing, permissions, and the rebind dance

A service name is the address. Names are validated before they ever touch the filesystem: non-empty, at most 64 bytes, and drawn only from a–z, 0–9, - and _. That rules out traversal, hidden files, and case-folding surprises in one predicate, so a name can be joined into a path without further escaping.

ServiceBuilder::directory() overrides the base directory — tests use it, and so would a nested seat. build_with_listener() takes a listener the caller already owns, which is how a systemd socket-activated unit hands over LISTEN_FDS. Both paths end with the listener in non-blocking mode.

§4 — Peer authentication

The kernel vouches for the peer before any byte is read

Authorizer variants

VariantAdmitsUse
SameUid Only peers whose uid equals our euid. The default. Correct for every single-seat desktop service.
Uids(Vec<u32>) Our own uid, implicitly, plus an explicit list. A greeter or system agent that must serve a second account.
Custom(Box<dyn Fn>) Whatever the predicate says about the full Credentials. Group membership, cgroup checks, deny-lists.

Credentials also carries a best-effort pidfd. It is explicitly advisory — good for resolving an executable path, a cgroup, or for watching the peer die. It is never an authorization input, because a pid is reusable and a decision made on one is a race.

§5 — Wire format

Twenty bytes, little-endian, no options

Every frame is a fixed header followed by exactly len payload bytes. There are no optional header fields, no extension TLVs and no string keys on the wire; a frame's cost is its payload plus twenty bytes, always.

len: u32
Payload length in bytes, excluding the header. Checked twice — against the global MAX_FRAME during header decode, then against the connection's own ConnLimits::max_frame during reassembly.
kind: u8
One of the seven discriminants in §6. An unknown value is Malformed and kills the connection; it is never treated as an extension point.
fd_count: u8
How many descriptors this frame claims from the ancillary queue. Values above MAX_FDS_PER_MSG (16) are rejected at decode.
reserved: u16
Must be zero on the wire. Aligns the selector to an 8-byte boundary and reserves space for a future revision.
selector: u64
The method or event identity (§7). Zero on Reply and Error frames, which are correlated by req_id instead.
req_id: u32
Correlation token, allocated client-side starting at 1 and wrapping past zero. Zero on Notify and Event frames, which are never answered.

A real frame

A Request for add(a: 3, b: 4) on a service named macrotest, carrying request id 7:

0x0002 00 00 00len = 2 — the postcard body is two bytes
0x0400kind = 0 — Request
0x0500fd_count = 0
0x0600 00reserved, must be zero
0x0874 fb 6c 85 c2 b5 c7 8aselector = 0x8ac7b5c2856cfb74 — FNV-1a 64 over "macrotest\0add\0(a : u32, b : u32) fds() -> (u32)"
0x1007 00 00 00req_id = 7
0x1403 04payload — postcard varints for a = 3, b = 4

Twenty-two bytes total for a two-argument call. The reply is twenty bytes of header plus one varint. Postcard contributes no field names, no type tags and no framing of its own — the header already says how long the body is, so the encoder is free to be minimal.

§6 — Message kinds

Seven discriminants, and who is allowed to send each

#KindDirectionselectorreq_idSemantics
0Requestclient → service method≥ 1 Expects exactly one Reply or Error bearing the same req_id.
1Notifyclient → service method0 Fire-and-forget. Never answered, not even on handler failure.
2Replyservice → client 0echoed Postcard-encoded return value; () serialises to an empty payload.
3Errorservice → client 0echoed Payload is a postcard RemoteError { code, message }.
4Subscribeclient → service event≥ 1 Empty payload. Acked with an empty Reply, or Error{4} at the cap.
5Unsubscribeclient → service event≥ 1 Always acked, whether or not the subscription existed.
6Eventservice → client event0 Server push, delivered only to subscribers. Lossy under backpressure.

Direction is enforced, not documented. A client that sends Reply, Error or Event is dropped by Server::next_request; a service that sends Request, Notify, Subscribe or Unsubscribe raises Malformed("server sent client-only frame") in Client::handle_readable. The bus is strictly asymmetric — there are no callbacks from service to client, only events a client asked for.

Subscribe and Unsubscribe never reach application code. The server consumes them inside next_request, updates the peer's subscription set, and acks — so a protocol handler has no way to forget to implement them.

§7 — Selectors

A method's name on the wire is its whole signature, hashed

What drift looks like

Change b from u32 to u16 and recompile only the client:

BuildSignature hashedSelector
service(a : u32, b : u32) fds() -> (u32)0x8ac7b5c2856cfb74
stale client(a : u32, b : u16) fds() -> (u32)0xa42b8515ae7a71e2

The dispatcher's selector comparisons all miss, it falls through to the tail, and the client gets Error { code: 1, message: "unknown method selector 0xa42b8515ae7a71e2" }. Compare that with a length-prefixed name plus a positional argument tuple, where a widened integer is decoded as whatever the next bytes happen to be.

Event selectors are derived the same way, with the method component spelled "event.<Name>" and the field list as the signature — so an event and a method can never share a selector, and adding a field to an event retires the old one.

  • The hash is a const fn. Selectors are link-time constants, so dispatch is a chain of u64 comparisons a compiler can lower to a jump table.
  • FNV-1a is not collision-resistant against an adversary — it does not need to be. A hostile peer that guesses a valid selector still only reaches a method it was already authorized to call, and every payload is bounds-checked on decode.
  • The NUL separators are not decoration: without them selector("ab","c",…) and selector("a","bc",…) would hash identically. There is a test for exactly that.

§8 — Message flows

Four exchanges, and that is the whole protocol

Subscription state is per-connection, not per-process: two clients in the same program holding two Clients subscribe independently. Server::emit walks live peers, skips anyone whose subscription set lacks the event's selector, and encodes the payload once for all of them.

§9 — Descriptor passing

Descriptors travel beside the stream, not in it

SCM_RIGHTS ancillary data is attached to a sendmsg(2) call, and the kernel associates it with the byte at that point in the stream — not with any framing the application invented. Reconciling those two is the subtlest part of the implementation.

  • MSG_CMSG_CLOEXEC on every receive: a descriptor is never visible across an exec in the window before the application sets the flag itself.
  • Received descriptors are OwnedFd from the moment they leave the control buffer, so every error path — malformed header, oversize frame, missing fd, poisoned connection — closes them by drop.
  • MSG_CTRUNC means the kernel had more ancillary data than the control buffer could hold. The connection is poisoned: a truncated fd set cannot be reconciled with frame boundaries.
  • FD_QUEUE_CAP is 64 — four frames' worth. A peer that sends descriptors faster than frames is capped rather than allowed to exhaust the receiver's descriptor table.
  • The generated dispatcher hands each descriptor to the handler as a distinct OwnedFd parameter, so fds(image) in the protocol becomes image: OwnedFd in the trait method.

§10 — Connection machine

One socket, two queues, no blocking calls

Connection is the entire transport. It owns a non-blocking UnixStream and never calls poll, never spawns, never sleeps. The caller decides when the fd is ready and pumps it; every method returns promptly.

Poison versus close

The two failure modes are deliberately distinct. Close is the peer going away normally — EOF, EPIPE, ECONNRESET. Queues are left intact so already-parsed messages can still be drained. Poison is a protocol violation: the inbox, outbox and descriptor queue are all cleared, every held descriptor is closed, and the socket is shut down in both directions. Nothing a misbehaving peer sent is ever acted on after the violation is detected.

§11 — Backpressure

Requests push back; events are dropped

That asymmetry is the whole policy. A request is something the caller is waiting on, so it must not be silently dropped: the pressure travels back up the connection until the caller's own send blocks. An event is a notification about state the subscriber can re-read, so a subscriber that cannot keep up loses events rather than stalling the service that is trying to notify it.

§12 — Server & peers

Peer handles that cannot be confused after a reconnect

Peers live in a slot vector, and freed slots are reused. That makes a bare index dangerous: an event-loop callback holding a stale index would address whoever landed in the slot next. PeerId pairs the index with a generation counter that is bumped on every release.

The pump contract

Server takes &mut self everywhere and holds no interior mutability, so exactly one owner drives it. An integration is always the same five calls: 

// listener readable
while server.accept()?.is_some() {}      // drain the backlog

// peer readable / writable
server.handle_writable(id)?;            // flush the outbox
server.handle_readable(id)?;            // fill the inbox
while let Some(msg) = server.next_request(id) {
    dispatch(&mut app, server, id, msg)?;  // Subscribe/Unsubscribe never reach here
}
server.reap(id);                        // true once EOF is drained; peer removed

handle_readable and handle_writable remove the peer themselves on error, so a caller that gets an Err only has to deregister its event source — there is no window where the loop and the server disagree about who is connected. reply and reply_err flush opportunistically, which keeps request/reply latency at one syscall in the common case where the socket is writable.

§13 — Client

Pending handles, typed replies, queued events

Client::start_request returns a Pending<R>: a request id plus a PhantomData<R> recording the reply type the method promised. It is #[must_use], so dropping one without resolving it is a warning rather than a silent leak of a correlation slot.

  • take(&pending) is the non-blocking harvest: Ok(None) while the reply is outstanding, Ok(Some(R)) once it arrives, Err(Disconnected) if the connection died first.
  • wait(pending, timeout) is the blocking form — a poll(2) loop that pumps both directions until the slot resolves or the deadline passes.
  • call_blocking composes the two for CLIs and tests.
  • Request ids start at 1 and wrap with .max(1), so zero stays reserved for unanswered frames.
  • Events queue separately from replies. next_event::<E>() scans for the first message matching E's selector and leaves everything else queued, so two subscriptions can be drained independently from the same connection.
  • An undecodable event is logged and dropped; an undecodable reply is a decode error returned to the caller, because someone is waiting on it.

blocking — a CLI or keybinding helper

let mut pad = crownpad::Client::connect()?;
pad.toggle()?;                                // notify — returns immediately
let pending = pad.volume()?;                   // request — Pending<u8>
let level = pad.wait(pending, TIMEOUT)?;       // u8

tokio — feature tokio

let mut c = AsyncClient::connect("crownotify")?;
c.subscribe::<crownotify::Dismissed>().await?;
let id = c.call::<crownotify::send>(&crownotify::send {
    song_name: "Rêverie".into(),
    percentage: 80,
}, vec![]).await?;
let ev = c.next_event::<crownotify::Dismissed>().await?;

§14 — protocol! macro

One definition, both ends, no hand-written glue

A protocol is declared once. The macro generates the argument structs, the client, the server trait and the dispatcher from the same tokens, so the two ends cannot be edited out of step — and because the Handler trait has one required method per protocol method, adding a method to the definition breaks the service's build until it is implemented.

Dispatch behaviour, precisely

ConditionResult
Selector matches, kind matches, payload decodesHandler is called; its Ok is encoded into a Reply, its Err into an Error frame.
Selector matches but kind is wrong — a Notify sent at a fn methoddrop_peer. The peer is not speaking this protocol.
Payload fails to decodedrop_peer. The selector asserted a shape the bytes do not have.
Fewer descriptors than the method declaresdrop_peer, closing any descriptors already claimed.
Reply fails to serialiseError { code: 2, HANDLER } — the peer's fault it is not, so the connection survives.
No selector matches, kind is RequestError { code: 1, UNKNOWN_METHOD } naming the selector in hex.
No selector matches, kind is NotifySilently ignored — there is nobody to answer.

service side — calloop, sharing the app's existing loop

let server = ServiceBuilder::new("crownpad").build()?;
let ipc = CalloopService::insert(&handle, server, |app, server, peer, msg| {
    crownpad::dispatch(&mut app.pad, server, peer, msg)
})?;
ipc.emit(&crownpad::Visibility { visible: true })?;

§15 — Runtime adapters

The core knows nothing about any runtime

AdapterSurfaceFits
adapter::calloop CalloopService::insert, emit, with_server A compositor, panel or widget that already owns a calloop loop and must not run a second runtime beside it.
adapter::tokio AsyncClient, serve Async services and clients on AsyncFd.
adapter::smol AsyncClient, serve The same surface on async-io, for smol-based binaries.
blocking blocking::serve, Client::wait CLIs, tests, and daemons that run a serve thread and bridge into their UI loop over a channel.

The calloop adapter carries the only genuinely intricate code in the crate. calloop reaches a source's poll interest through the owning dispatcher, which is mutably borrowed for the duration of that source's own callback — so a peer could never adjust its own registration from the one place that learns the outbox drained. The adapter keeps each peer's interest in an Rc<Cell<Interest>> read at registration time; the callback writes the cell and asks calloop to update, which defers the re-registration until after the callback returns. Removals are handed back as a PostAction for the same reason.

§16 — Errors

Two error types, on opposite sides of the socket

Error is local: what went wrong in this process. RemoteError is the only error that exists on the wire, and it is deliberately tiny — a u32 code and a message — because a rich error type would be a second schema to keep in sync across the connection.

3UNAUTHORIZEDReserved for handler-level policy; connection-level denial happens at accept, before a frame exists.

§18 — Invariants

What each side may assume

A service may assume

Every connected peer passed the authorizer before a byte was read, and its uid and gid are the kernel's answer, not the peer's claim.

A service may assume

Any message reaching a handler had a matching selector, a matching kind, a payload that decoded, and exactly the declared number of descriptors.

A service may assume

No peer can grow its queues without bound: caps on connections, subscriptions, inbox depth, outbox frames and outbox bytes are all enforced beneath the application.

A client may assume

Each Request gets exactly one Reply or Error with its own req_id, or the connection closes. There is no third outcome.

A client may assume

A reply that decodes is the type the method declared, because the selector that addressed the method also encoded the return type.

Both may assume

Every descriptor received is an OwnedFd from the moment it arrives, so no error path leaks one.

Nobody may assume

That an Event was delivered. Events are best-effort and dropped for any subscriber whose outbox is full.

Nobody may assume

That a Notify was processed. It is unanswered by construction; anything worth confirming is a fn, not a notify.
